# 功能模块说明书

> **这份文档讲什么**：仓库里每个功能模块「是什么、怎么工作、给使用者什么保证、限制在哪」，以及关键取舍的一句话理由。
> **给谁看**：想深入理解这个项目、或准备动手改代码的贡献者；只想把工具跑起来的用户请看下一行的入口。
> **日常使用请先看**：[`README.md`](../README.md)（安装与上手）与 [`client/vscode/README.md`](../client/vscode/README.md)（按症状排障）。
> **想找「改代码去哪」**：看 [`ARCHITECTURE.md`](../ARCHITECTURE.md) —— 它负责代码索引，本文负责功能本身。

项目一句话：一个特化的 Unity ShaderLab / HLSL 语言服务，对当前编辑的着色器做**真实的 DXC 编译**（微软的 DirectXShaderCompiler），报出与编译器一致的错误，并把每条诊断的坐标精确换算回源文件的行列。

四条长期约束贯穿全文：

- 服务端是**原生发布**（提前编译成原生可执行文件，用户不需要安装 .NET 运行时）；
- **零第三方依赖**（需要的能力自己写，构建机可完全离线）；
- **标准输出只允许出现协议帧**：任何日志与调试输出都必须绕开传输通道，否则会污染编辑器与服务端的通信；
- 不做全量工程符号索引 —— 这是为低配设备做的取舍，只保证「打字那一刻的诊断准」。

每一节的内部结构相同：一句话说明功能 → 怎么工作 → 保证与限制 → 代码入口；带取舍的地方多一段「关键决策」。代码入口只列 1~3 个最关键的文件，完整索引见 [`ARCHITECTURE.md`](../ARCHITECTURE.md)。

> 阅读提示：代码注释与提交信息里会出现开发期的「模块 1~13」编号；本文按功能组织，不认识这些编号也不影响阅读。

## 一次诊断的完整流程

```text
打开 / 打字 / 保存
  → 服务端保存一份文档副本，行级比较找出「首个改动行」（本次分析的重点行）
  → 防抖：打字连击合并为一次分析；保存立即穿透并抢占在途分析；打开立即分析
  → 切片：把 ShaderLab 切成一个个编译单元（Pass / 程序块），收集变体与 include
  → 路径解析：把 Packages/… 这类虚拟路径映射到磁盘上的真实文件
  → 文本装配：注入宏与 #line 锚，拼出可直接交给编译器的一段文本
  → 编译：每个单元按顶点 / 片元阶段分别真实编译
  → 归属与降噪：坐标换算回本文件行列、去重、外部头文件报错重映射
  → 按 Pass 合并后整份推送 → 编辑器画红线
```

改任何代码前，先认清自己动的是哪一条「流」：

- **诊断流**（打开 / 打字 / 保存触发）：打字时只算重点单元，保存时全量。任何优化都不允许把磁盘扫描或 DXC 编译塞进交互路径。
- **交互流**（补全 / 导航 / 悬停）：预算 3~5 毫秒，只允许读内存中已有的数据，必须做到「永远不等编译」。
- **红线**：任何一步的失败都必须有可读的结局（禁止静默吞掉）—— 这是全项目最重要的一条产品约束。

两条流的预算量级不同：交互流在毫秒内完成；保存流的全量诊断在官方语料上约 0.3 秒量级，允许慢，但不允许把这份开销提前泄漏到打字路径。

标签语义校验是诊断流程里的一个旁路：在切片之后、装配之前做纯文本检查，不触碰编译器，所以打字快路径也能带着它。

## 实时诊断引擎

**功能一句话**：把一个 `.shader` 文件切成若干编译单元，拼成编译器可以直接吃的文本，真实编译，再把每条诊断的行列换算回源文件 —— 这是「真的编译」这句话的全部内容。

### 怎么工作

1. **切片**：一次线性扫描完成结构识别，产出编译单元（起止行、入口名、变体关键字、include 记录）与切片阶段自身的诊断（块 / 注释 / 字符串未闭合等）。词法上做三件必须做的事：识别词边界（`UsePass` 路径里的 `Pass` 子串不算结构）、跳过注释与字符串（它们里面的伪标记不算结构）、跟踪花括号深度进入 / 退出 Pass。`HLSLINCLUDE` 这类共享块的作用域是「本文件内所有同类程序块」，因此要整篇扫完再回填 —— 官方 URP 就把共享块写在第一个 SubShader 之前。老式 CG 写法（`CGPROGRAM` 且没有引用现代管线头文件）会被标记「抑制派发」并给出可读原因：老式写法喂给现代编译器只会大面积误报。
2. **宏注入**：变体关键字按三条规则变成宏 —— 选中的关键字写 `#define K 1`（必须带值，裸定义会让宏判断本身报错）；同组的未启用关键字**完全不定义**（定义成 0 会让「是否定义」类的判断恒真，URP 会立刻渲染错）；所有声明过的关键字都补一个「已声明」标记宏。选变体时跳过 `_` 占位符、取第一个真实关键字 —— 选中「关闭变体」会把 `#if defined(...)` 保护的代码整段裁掉，造成「代码写错但编译器给虚假通过」。阶段维度另有硬约束：阶段宏恰好一个成员；非光追派发放到显式取消光追阶段宏（官方公共头文件里有一处依赖「未定义即为 0」的裸表达式）。
3. **文本装配与锚定**：渲染文本只由「段」列表生成（注入段 = 宏与 `#line` 锚；锚定段 = 共享块 / Pass 内容），绝不事后修补。`#line` 指向 Unity 逻辑路径（`Assets/…`、`Packages/<包>/…`）而不是磁盘路径 —— 可读、抗包缓存版本漂移；磁盘路径另外附在诊断信息里供定位。同一行内改字节（把 `#include_with_pragmas` 降级为普通 include、把虚拟路径换成物理路径）会移动列号，所以列映射按「公共前缀 / 引号差异 / 路径 / 尾部」分段投影。装配失败有明确分类：未闭合块、抑制派发、缺依赖、无可编译内容；**中止也必须带原因上报**，不允许出现「文件坏了但一条诊断都没有」。
4. **编译**：进程内调用真实编译器；一个 Pass 的顶点与片元入口分别编译一次（两个阶段的宏集不同，同一处错误可能报两次，展示时按位置去重）。与编译器的互操作层是手写的（原生发布下无法使用自动生成的包装）。三条红线：绝不把未重写的虚拟路径喂给编译器（死链 include 中止整个编译单元并上报原因，绝不猜测）；绝不传「全警告 / 警告即错误」这类开关（URP 头文件会刷满无意义的未知 pragma 警告）；诊断一律读编译器接口自带的错误缓冲，绝不解析命令行工具输出的文本（那是本地编码的非 UTF-8 文本）。
5. **归属与降噪**：坐标要过三站 —— 磁盘物理坐标（编译器的输入）→ 装配后渲染文本坐标 → 源文件坐标。因为装配时写了 `#line`，编译器报的行号就是源文件行号；列号是 UTF-8 字节口径，要换算成编辑器使用的字符口径（这是反复踩到的坑点：两套坐标系不同）；被改写过的行再投影回源列；映射不回去时按「工具内部缺陷」上报而不是静默。降噪：note 级默认丢弃（多指向头文件内部声明，对着色器作者是噪声）；`#pragma message` 产生的警告按「源代码行文本」过滤；外部头文件的报错优先重映射到主文件对应的 `#include` 行，深层依赖标注「通过谁引入」。
6. **整篇装配**：保存路径一次装配整篇文档的全部编译单元，报告里给出「组装成功 / 按策略抑制 / 中止」三类结局与逐条原因。

### 保证与限制

- **黄金判据**：URP 官方 `Lit.shader` 在正确宏集下**零 Error**；官方 URP 包在切片阶段**零诊断**。任何规则如果在官方语料上误报，正确做法是把规则降级，而不是放宽断言。
- **每一个代码块都必须有确定结局**：编译单元总数 = 组装成功 + 按策略抑制。这条等式同时能抓住「悄悄漏掉一个块」和「把失败混进抑制里蒙混过关」两种退化。
- **编辑闭环成立**：打开一个坏文件 → 改对错误 → 保存，对应红线消失。
- 诊断码口径：引擎与装配层用 `MS00xx`（如 `MS0001` 依赖缺失、`MS0002` 未闭合块、`MS0007` 装配注入段报错 = 工具自身缺陷）；切片阶段诊断用 `SL0001`~`SL0005`，会与编译诊断合流展示。
- 死链 include 的诊断文案要人话：点明这是「依赖扫描层」的结论，不误导用户去改预处理代码。
- 性能量级（真实 URP 语料）：切片本身是每文件零点几毫秒量级；225 个编译单元装配约 26 毫秒；官方 `Lit.shader` 全量分析墙钟约 0.3 秒（并行编译后）。
- 限制：保存路径目前是全量扫描，尚未按文本变化缩减要重编译的单元；include 闭包（一个文件经 include 可达的全部文件）未缓存，同一头文件被多个 Pass 引用会重复解析；平台宏拿不到真值时按「推定」处理并如实标注，不当已证事实；光照贴图编码这类推导留白 —— 不做凭空推定。

### 代码入口

- `src/MicroShader.ShaderLab/ShaderLabStateMachine.cs` —— 切片
- `src/MicroShader.DiagnosticEngine/VirtualTextAssembler.cs` —— 装配与锚定
- `src/MicroShader.DiagnosticEngine/NativeCompilerGateway.cs` —— 编译器调用

### 关键决策

- **include 处理器为什么自研**：编译器自带的处理器解析不了 `Packages/…` 虚拟路径，而包内文件自己写的虚拟路径我们无权改写 —— 只能自己实现一个「按工程虚拟文件系统解析」的处理器。
- **为什么坚持真实编译**：只有真实编译能报出隐式截断、未声明符号、类型不匹配这类真错，并把坐标精确回源；正则匹配或内置符号表方案做不到这一点。
- **为什么「绝不把虚拟路径喂给编译器」**：否则故障会以无关错误的形式四处冒头；宁可中止该单元，并明确报「依赖缺失」。

## Unity 工程与包路径解析

**功能一句话**：把工程里的包和 `#include` 虚拟路径解析成磁盘上的真实文件 —— 这是「真的编译」能成立的前提。

### 怎么工作

1. **五类包来源**，优先级从高到低：工程 `Packages/` 实体目录（正在开发的包）→ 工程清单里 `file:` 指向的本地包 → git 包（在包缓存里，目录名带提交哈希）→ 包缓存目录（从包管理器下载的正式包）→ Unity 编辑器自带的内建包目录。「工程优先、缓存兜底、内建垫底」必须在实现里真正落地：实测大量包名会同时存在于内建与缓存两处，只用一条路径去找必然出错。
2. **`#include` 四规则**：以 `Packages/<包>/…` 开头的查包根；以 `Assets/` 开头的查工程资产目录；裸名与相对路径以「包含方文件所在目录」为基准；裸名兜底查编辑器自带的公共头文件目录（由编译器侧搜索路径承担）。
3. **两种解析模式**是这里最关键的性能裁决：编译热路径只做纯路径演算（零磁盘 I/O、零锁、零分配）；「磁盘上到底有没有这个文件」只留给依赖扫描上报层去探。热路径的结论与编译器自身的解析行为保持一致。
4. **一次构建、无锁读取**：先把整个工程扫成一份不可变快照，读端一次原子读取拿到；磁盘变化由监视器给出重建提示。Unity 桥接在线时，还能额外拿到编辑器实测的宏状态。
5. **Unity 安装目录定位三层**：Unity Hub 配置 → 工程里的编辑器实例记录 → 注册表（键名带完整版本号）。三层全失败不算致命错误：只影响兜底规则，实现会降级并上报。
6. **`Library/` 目录下的桥接端点**（编辑器运行后才出现）不靠目录监视，改用低频心跳做指纹比对 —— 监视整个 `Library/` 被设计禁止，而该目录在编辑器首次运行前并不存在。

### 保证与限制

- URP 官方包内部的 include 图 100% 可解析（实测）；未命中一律给出明确失败原因，**不猜测、不静默丢弃**。
- 包名与来源以工程包锁文件为权威；五类来源与破损工程清单的降级都有固定用例覆盖。
- 冷启动建索引是毫秒量级，因此**不做**二进制快照缓存 —— 先用实测砍掉，而不是先实现再优化。
- 限制：编辑器日志拿不到平台宏真值（实测无命中）时按推定标注；一个游离的 `.hlsl` 文件属于哪个工程需要工作区上下文，暂不覆盖。

### 代码入口

- `src/MicroShader.ContextEngine/VfsIndexBuilder.cs` —— 工程扫描与快照
- `src/MicroShader.ContextEngine/IncludeResolver.cs` —— include 解析规则

### 关键决策

- **包名绝不靠「@ 版本号」正则推导**：正式包与 git 包的缓存目录形态完全一样，必须看工程包锁文件里的来源字段（并有固定用例把这条路钉死）。
- **安装定位为什么允许失败**：三层全失败只影响兜底规则，工程内路径解析完全不依赖它 —— 上报后优雅降级，而不是拒绝启动。

## 响应式调度

**功能一句话**：决定「什么时候分析、分析哪一版、哪次结果算数」—— 打字时合并连击，保存时立即穿透，过期的结果一律丢弃。

### 怎么工作

1. **三类触发语义不同**：打开文件立即分析（首次诊断不加延迟）；打字防抖合并（默认 300 毫秒，自动夹取在 200~500 毫秒之间）；保存立即穿透并抢占在途任务；关闭文件立即清空红线。
2. **版本栅栏**（丢弃过期结果）：每次事件到达就把该文档的代际号加一，分析前后各校验一次；代际号只增不减，同时覆盖「重复派发」「旧结果迟到」「保存超越在途」三种情况。跨会话用全局单调、永不复用的会话编号隔离 —— 关闭再打开后客户端版本号会回到 1，只靠版本号会撞号。
3. **诊断缓存按内容寻址**：以「装配文本内容」为键，内容没变的编译单元直接复用结果，跳过重编译。
4. **整份合并再发布**：编辑器的诊断是「整份替换」语义，因此按 Pass 维护诊断槽位、合并后整份推送 —— 只推当前 Pass 会把其它 Pass 的红线抹掉，用户看到的是闪烁。共享块被多个 Pass 重复报出的同一条诊断按位置去重。
5. **调度统计四项计数**（启动 / 发布 / 丢弃 / 合并）暴露给回归断言与排障读数。

### 保证与限制

- 连续打字合并为单次分析（回归用例以「连打 12 次 → 只产生 1 次分析」钉住）。
- **明确放弃「每次击键零分配」的宣称**：编辑器协议是每次变更发送整份文档，一份与文档等大的文本副本是协议选择本身的成本。这里只承诺「有界」—— 同一时刻只有最新快照会被派发。
- 限制：include 头文件的内容变化不在缓存判据里；保存无法取消已进入编译的分析（只能等它结束再丢弃）；头文件磁盘变化的失效粒度过粗 —— 任何着色器家族文件变化都会让所有已打开文档全量重算。这是刻意选择「宁可多算不漏算」：漏算的症状是「改了头文件红线不消失」，用户会认为工具坏了；实测这不拖慢补全，代价只是白算。

### 代码入口

- `src/MicroShader.CoordinationEngine/Scheduling/CoordinationScheduler.cs` —— 防抖与仲裁
- `src/MicroShader.DiagnosticEngine/ShaderDiagnosticEngine.cs` —— 内容寻址缓存

### 关键决策

- **防抖为什么是 300 毫秒**：同类工具（clangd、rust-analyzer 这一档）的量级在几十到几百毫秒，最初设想的 2.5 秒是离群值，打字会明显滞后。
- **为什么用代际号而不是比对客户端版本号**：客户端版本号会回绕（重开文件），代际号只增不减，才能同时覆盖三种过期场景。
- **为什么缓存按内容哈希而不是按版本号**：版本号相同不代表内容相同（跨文档），内容变了之后版本号也可能被客户端复用 —— 内容哈希才是「要不要重编译」的正确判据。

## LSP 传输与会话管理

**功能一句话**：编辑器与服务端之间走标准 LSP（Language Server Protocol）协议：接收 JSON-RPC 报文、维护文档副本、按状态机应答请求与退出。

### 怎么工作

1. **分帧**：报文头声明正文长度，按 UTF-8 字节数读取；头 / 正文分批到达时挂起等待，绝不把半截当一帧。分帧失败视为**不可恢复**、直接终止会话 —— 绝不「按字节搜索重新同步」：报文正文（HLSL 注释、诊断文本、用户正在写的内容）完全可能字面包含类似报文头的文本，搜索会同步到正文内部，此后帧边界永久错乱且无法自愈。
2. **零反射**：请求参数直接按 UTF-8 逐字段读取，响应直接写进输出缓冲（没有可被反射序列化的中间对象）—— 这是原生发布与性能的双重要求。
3. **文档副本（影子文档）**：服务端保存的文档副本以「不可变快照 × 版本 × 会话编号」发布，分析线程按派发时携带的版本读取，读取期间上游再改也不会读到半新半旧的内容。行级比较算出「首个改动行」作为分析重点 —— 标准协议里没有光标 / 焦点通知（检索规范全文，相关字段命中为零），焦点只能靠启发式（最近发生变更的文档）。
4. **会话状态机**：未初始化就发来的请求回协议约定的错误码；收到过关机请求再退出 → 退出码 0，否则 1；关机后请求回错误而不是静默。出站是单写者队列，一次写 + 一次刷新原子提交整帧，靠刷新的完成标志感知对端已断开（不能指望「写失败立刻抛异常」）。
5. **只改空白 / 注释的编辑直接跳过分析**，不浪费一次编译。
6. **初始化应答显式声明**「整份文档同步」与 UTF-16 位置编码；不宣告拉取式诊断、保存附带文本这两种用不到的能力。
7. **文档关闭立即回收副本并推空诊断**（先清红线、再拆状态，这是产品语义，不是实现顺序）。

### 保证与限制

- 中文等非 ASCII 路径与内容按 UTF-8 字节正确分帧与还原。
- 原生发布的硬约束：读循环里任何未处理的异常 = 进程立即终止且没有托管转储，因此报文解析与处理有双层兜底：处理失败回通用的内部错误应答，兜底自身不抛异常并落盘留痕。
- 取值层同样设防：数字字段一律走「尝试解析」而不是「直接取」，畸形参数（非字符串的请求编号、越界坐标）只回错误应答、不拖垮会话。
- 限制：取消请求目前只解析记录（本服务当前不主动向客户端发起请求，没有可取消的出站请求）；出站背压偏保守（队列满即判定断开 —— 若生产上出现误判，应改为「诊断类帧可合并、响应类帧不丢弃」的分级策略）。
- 文档同步模式是「整份发送」；若将来改成拉取式诊断模型，应改为同版本去重 + 结果编号，而不是保留秒级延迟。

### 代码入口

- `src/MicroShader.CoordinationEngine/Session/LspServerSession.cs` —— 协议状态机与路由
- `src/MicroShader.CoordinationEngine/Transport/StdioFramingChannel.cs` —— 分帧

### 关键决策

- **为什么不引入第三方响应式框架**（最初设想使用 Cysharp/R3）：它没有声明原生发布兼容，把这样的框架放在全系统最热的调度路径上，风险收益不划算；真实需求只是「可重置的延迟 + 取消」，几十行标准库代码即可等价实现，而且语义可以被无头自检完全覆盖。
- **文档副本为什么用一把普通锁**：写入方只有一个线程，为省一次无竞争的锁而去冒数据竞争的风险，是在优化错误的对象。

## 可观测性与排障设施

**功能一句话**：一个崩溃后还能读出现场的「内存日志缓冲」：固定 512KB 内存、自动转储、把原生输出与协议通道物理隔离、日志限流防止刷屏。

### 怎么工作

1. **无锁环形日志**：固定 512KB 内存的环形缓冲，写满覆盖最旧记录；写者不阻塞。写入协议把「全局序号」编进「每次写入的版本标记」里 —— 一次原子读同时回答「这条正在被写吗」与「槽里是不是我要找的那条」；读者发现记录不完整就跳过，**绝不读出半截数据**。
2. **零分配的日志格式化**：插值写法的日志在热路径上实测零分配、零装箱。
3. **标准输出隔离屏障**：原生代码的输出（如 C 运行时的直接打印）与协议传输通道物理分开；默认**不**封标准输出（那是命脉），需要时显式开启并把真正的通道预先捕获出来。标准错误（stderr）落临时文件而不是丢弃 —— 编译器命令行工具的错误走标准错误且是本地编码（GBK），落文件才能事后并入转储，但诊断文本仍以编译器接口返回的为准，stderr 只作旁证。
4. **崩溃转储**：写到 `%LOCALAPPDATA%/MicroShader/dumps/`（不放系统临时目录 —— 会被系统清理、被 CI 忽略），同卷临时文件 + 原子替换；磁盘满时不重试、不留异常，把内存里最后几条错误通过编辑器通知弹出。转储是结构化 JSON，机器可解析，可直接作为排障附件；文件里写明「按最大写入速率推算的窗口时长」作为参照，免得事后误判「为什么崩溃前的日志没了」。
5. **出站纪律**：调试级日志只留在内存缓冲（永不打扰用户）；追踪级仅在客户端显式支持时输出，否则彻底丢弃；其余日志限流（默认 1 秒 20 条），超出的聚合为一条「日志过多，其余已缓存」的定长提示。
6. **日志脱敏**：入队时就把用户主目录替换为 `~/`（正反斜杠两种写法都认），转储文件可以直接分享。
7. **崩溃钩子挂两个兜底点**（正常退出与 Ctrl+C），强杀不可捕获属已知边界。

### 保证与限制

- 回归断言钉住的性质：不读出撕裂记录、可读条数不低于容量的九成、两万次插值写入零分配。
- 标准输出屏障的三条顺序约束：必须在任何标准输出访问之前安装、绝不无条件封住标准输出、先预捕获真通道再动手 —— 顺序错了屏障就失效。
- 已知取舍：极端争用下会「丢读」（同一槽位被覆盖后读者判定无效而跳过），但绝不会读到撕裂数据；丢读率尚未实测 —— 生产环境若发现日志缺失，先量这个数再谈改协议。
- 已知边界：Windows 强杀进程不可捕获；隔离屏障管不到「初始化时已缓存自己输出句柄的库」；原生标准错误文件不轮转，只在读回时截取尾部。

### 代码入口

- `src/MicroShader.ObservabilityEngine/LogRingBuffer.cs` —— 环形日志
- `src/MicroShader.ObservabilityEngine/CrashFlightRecorder.cs` —— 崩溃转储

### 关键决策

- **内存日志工程刻意不引用任何其它工程**：它必须比它记录的对象活得久（崩溃时其它部件可能已经不可信）；外部状态由调用方反向注入，而不是它去依赖业务类型。

## 智能补全

**功能一句话**：在 HLSL 代码里补全成员、结构体分量、变量 / 函数 / 宏前缀、URP 头文件里的类型与函数、内置引擎变量与向量分量。

### 怎么工作

1. **候选来源按优先级**：本文件符号（容错扫描，语法半成品也要能用）→ include 链预热缓存（`Varyings` 这类定义在 URP 头文件里的结构体）→ 兜底同步扫描（刚打开文件、预热还没赶上时救急，只扫直连的 include）→ 引擎内置变量表（时间、相机位置、变换矩阵等约 50 条常用 uniform）→ 内建向量族的成员分量。
2. **预热是离线扫描**：打开文档时把「扫 include 链、抽符号」排进后台队列，补全侧只读缓存、**绝不碰磁盘**；关闭文档即失效。新写的 `#include` 不必等保存即生效。
3. **触发形态**：点号后的成员访问；变量前缀（含 include 链里的 URP 函数与结构体、`#define` 宏）；括号内补全（缓冲声明、采样器声明处）；纹理派生名补全（`_X_ST` / `_X_TexelSize` 这类由纹理声明推导的名字）。
4. **符号缓存分两级**（文件层与文档层），同一文件在不同文档里的重复扫描只发生一次。
5. **缓存同步**：被 include 的头文件在磁盘上变化时，符号缓存随之失效（首次命中的扫描结果会写回缓存）。

### 保证与限制

- 延迟：补全中位在 0.1 毫秒量级，远低于交互流 3~5 毫秒预算；服务端往返恒定 1~4 毫秒，**不是瓶颈**。
- 唯一可复现的「超过 1 秒」出现在编辑器窗口刚打开的头 20~30 秒（扩展激活高峰期争用，与本服务无关）。
- 兜底扫描只扫直连 include（数量由设置项控制），最坏情况也不拖垮响应。
- 限制：成员访问**只支持一层** —— `v.posOS.` 这种嵌套成员访问目前返回 0 项；扁平符号表没有词法作用域，同一文件跨函数的同名变量按「文本上最后一条声明」胜出；条件编译分支里的声明一律照收（不求值 `#if`）；URP 自己声明的 uniform 依赖现场包采集覆盖；超大单个代码块（40 万字符级）的索引重建仍超出 5 毫秒配额，根治需要位置作用域化的索引（架构级后续项）。

### 代码入口

- `src/MicroShader.IntelliSenseEngine/IntelliSenseService.cs` —— 补全与悬停入口
- `src/MicroShader.IntelliSenseEngine/IncludeSymbolWarmer.cs` —— include 链预热

### 关键决策

- **为什么不用编译器自带的智能感知接口**：实测它跑的是 C++ 前端（HLSL 语义被按 C++ 规则判定：三目运算符按 C++ 报错、`saturate` / `lerp` 被判未声明），前缀补全六种形态一律 0 候选；它唯一独占的能力（include 内类型的成员补全）已由自研的 include 链预热覆盖，而且快得多（微秒级）。延迟（个位数到几十毫秒）不是否决理由，语义错误才是。

## 导航

**功能一句话**：按 F12 跳转到定义、`#include` 行可点击、文档大纲 / 面包屑、折叠范围（兼作编辑器「粘滞滚动」的数据源 —— 粘滞滚动指编辑器顶部常驻显示当前所在作用域的功能）。

### 怎么工作

1. **F12 候选来源按优先级**：本文件当前块与生效的共享块（离光标最近的声明优先）→ include 闭包（越近的 include 越优先；重载函数 1→N 全部返回）→ 宏别名解包（对象式宏迭代到定点，最多 8 层；宏定义处与展开后的实现处都给候选）。
2. **`#include` 链接两段式**：首屏只做纯词法扫描（零磁盘读），点击解析时才查盘；指向未安装包的链接返回「无法解析」而不是报错弹窗。两段式的收益：打开大工程首屏不读盘、不卡顿。
3. **大纲 / 面包屑与折叠范围**按大括号结构生成；折叠范围只按结构走，控制流语句不会进入粘滞条目。客户端把折叠范围配置为粘滞滚动的数据源。
4. 导航结果与补全同一形态：直接写进输出缓冲（零中间对象）。

### 保证与限制

- 精度：全部声明点的 F12 自洽 100%（两次独立运行一致）；延迟在 3 毫秒预算内覆盖约 100%（实测在 99.9%~100% 间波动，命中率不波动）。
- 大纲节点的层级与范围包含关系全部通过断言（含真实语料）。
- 限制：没有词法作用域（同名多声明用「最近声明优先」的启发式）；条件编译不求值；指向未安装包的 include 链接不可点击，这是按协议的正常行为而非错误。

### 代码入口

- `src/MicroShader.NavigationEngine/NavigationService.cs` —— F12 / 链接 / 大纲 / 折叠的统一入口

### 关键决策

- **宏解包为什么给两个候选（宏定义处与展开后的实现处）**：跳「宏本身」与跳「宏背后的实现」都是合理意图，让用户各取所需。

## 标签语义校验

**功能一句话**：发现编译器与 Unity 都不会报、但会**静默毁掉渲染**的 ShaderLab 标签拼写错误 —— 这是本工具最独特的一项能力。

### 怎么工作

1. **为什么需要它**：ShaderLab 的 `Tags` 是给渲染管线看的元数据，不进 HLSL 编译单元。`RenderPipeline` 的值拼错 ⇒ URP 不认领整个 SubShader，静默回退到内置管线（画面变粉）；`LightMode` 的值拼错 ⇒ 整个 Pass 变成永远不会被渲染的死代码。两者都不产生任何编译错误。两个标签还有层级含义：流水线标签写在 SubShader 级，光照模式标签写在 Pass 级。
2. **判定表从现场采集，不内置**：扫描工程已安装包内的 `.shader` 收集标签值，并额外从工程 C# 代码提取运行时动态注册的标签；辅以 Unity 文档确证的封闭集合、没有 SRP 包时的内置管线经典值。这三层全空时整体沉默。判定表随工程索引同批构建与重建。
3. **判定方式**：与已知值做近似比较，编辑距离阈值取 2 —— 能抓单字母替换 / 漏字（距离 1），又不至于把「故意写的另一个合法值」误报（合法值彼此的距离通常远大于 2）。`LightMode` 是开放集合（自定义值合法且常见），所以只在「精确不等但近似命中已知值」时报。
4. **五个诊断码**：

| 诊断码 | 级别 | 含义 |
| :-- | :-- | :-- |
| `SL0101` | Error | `RenderPipeline` 的值拼错了（近似某个已知值） |
| `SL0102` | Warning | `RenderPipeline` 的值未知（不属于任何已知值） |
| `SL0103` | Error | `LightMode` 的值近似某个已知值（疑似拼错） |
| `SL0104` | Warning | 封闭集合标签（值集合可枚举的标签）出现非法值 |
| `SL0105` | Error | 标签名拼错了 |

5. **沉默原则**：凡没有权威依据判定「非法」的标签名 / 值，一律不报。**零误报优先于零漏报** —— 误报会训练用户忽略全部诊断。
6. **位置与形态**：切片之后、装配之前的纯文本步骤，不触碰编译器，可进打字快路径；校验器无状态、线程安全、零分配。

### 保证与限制

- 黄金判据：URP 官方全部 `.shader` **零误报**（已满足）。管线接入后不注入判定表时一条都不多报（零行为漂移）。
- 热路径：单文件提取与校验均是 0.1 毫秒量级（预算 1 毫秒）；校验器零分配、多线程并发无竞争。
- **如实记录的不足**：包扫描 + 判定表构建实测约 101 毫秒，超出 20 毫秒预算 —— 属一次性冷启动、与工程索引同批进行，判定为可接受；标签提取侧每次约 456 字节分配，**未达「零分配」目标**（如实记录，待后续优化）。
- 已知误报边界：两个合法值彼此编辑距离 ≤ 2 时可能误报（只在「精确不等但近似命中」时报，其余沉默）。
- 非目标（明确不做）：`RenderType` 这类自由文本、`Queue` 数值表达式、工程配置判断；标签名重复、C# 侧定义与 shader 侧使用不匹配也不校验。
- 尚未做的候选扩展：`FallBack` 路径存在性、`#pragma vertex/fragment` 入口函数存在性校验（评估为价值极高）、Pass 重名检查、编码器快速修复。

### 代码入口

- `src/MicroShader.ShaderLab/ShaderTagValidator.cs` —— 校验器
- `src/MicroShader.ShaderLab/ShaderTagSchemaBuilder.cs` —— 判定表采集与构建

### 关键决策

- **近似比较不引第三方库、也不上完整语法树解析**：需要做的只是识别键值对与短字符串近似比较 —— 引入硬件加速的比较库违反零第三方依赖且短字符串用不着，完整语法树解析属过度设计。近似比较用带宽截断算法实现，实测比朴素实现快数倍、分配低几个数量级。

## 客户端

**功能一句话**：编辑器里安装的两个薄客户端 —— VS Code 扩展（安装包内自带服务端与 DXC）与 Sublime Text 的声明式适配。

### 怎么工作

1. **VS Code**：打开 `.shader` / `.cginc` 文件时激活；**不绑定 `.hlsl`**（与已有的 HLSL 扩展共存；按文件名模式挂接，与语言归属解耦 —— 语言归属可能被其它扩展抢注）。二进制探测顺序：设置项指定的路径 → 扩展内置目录；可执行文件与编译器 DLL 必需，另一个验证器 DLL 可选。
2. **崩溃恢复**交给客户端基础库的内建仲裁（3 分钟窗口内 4 次上限），不自研。
3. **防孤儿**：客户端把父进程号传给服务端，服务端周期性检查，编辑器死了服务端自己退出；标准输入被关闭同样触发退出。
4. **Sublime**：两条安装路径（helper 包 / User 配置）二选一，脚本有互斥检测；F12 需手动键位覆盖；`#include` 超链接只能快捷键触发（该客户端没有鼠标绑定）。
5. **打包链**：一条脚本做「注入可执行文件 + DXC → 打包扩展」，一条脚本产出 Sublime 自包含安装包；扩展目录里的二进制落后时按哈希同步补齐。产物安装包本质是压缩容器，不再二次压缩。
6. **入门引导**：扩展内置三步上手引导（打开看诊断 → 敲点号看补全 → 可选接桥接），对应 30 秒验收。

### 保证与限制

- **离线可用**：安装包内置服务端与编译器，不需要 .NET、不需要联网；仅支持 Windows x64。
- 30 秒验收：状态栏出现「就绪」标识 / 敲点号出候选 / 在函数上按 F12 跳定义。
- 补全慢的排查顺序（已固化为文档）：先排除其它行内补全扩展的干扰，再看是否是窗口刚打开的头 20~30 秒 —— 服务端本身往返恒定为毫秒级。
- 三个性能设置（打字防抖毫秒数、编译线程上限、兜底扫描个数）只降低 CPU 峰值，不改变诊断结果。
- 无头回环能覆盖协议层，但覆盖不了客户端行为差异（例如某些客户端在初始化完成前就发通知），这部分依赖真机长时间使用验证。
- 兜底：命令「复制诊断信息到剪贴板」包含服务端路径、工程根与最近日志，排障时先拿它。

### 代码入口

- `client/vscode/src/extension.ts` —— 扩展主逻辑
- `scripts/package-vsix.ps1` —— VSIX 打包
- `client/sublime/README.md` —— Sublime 接入说明

## Unity 编辑器桥接

**功能一句话**：可选安装的 Unity 编辑器插件，把编辑器实测的全局宏与关键字状态实时同步给语言服务，让诊断用上真值而不是推定值。**不装，一切照常。**

### 怎么工作

1. **拓扑**：Unity 一侧监听本机回环地址的动态端口（最多 4 个连接、先到者胜），实际端口写进工程 `Library/MicroShader/endpoint.json` 发现文件（原子替换）；语言服务作为客户端外连 —— 「Unity 当服务器」的形态。发现文件放在 `Library/` 而不是系统临时目录：后者在编辑器退出时会被清空。
2. **发现与判活**：进程号 + 编辑器启动时间组合判活，进程名只作辅助；读不到信息时降级为告警、**绝不删除发现文件**（删了会把正常运行的工具踢下线）。连接前必查「域重载中」标志 —— 重载窗口内端口已被释放，硬连会撞上占用该端口的其它进程。
3. **读端四不原则**：不删、不抛、不猜（版本不认识即拒绝）、不越界（只读自己工程根下的文件）。
4. **服务端两个使用路径**：动态宏注入（把编辑器实测的宏写进装配的注入段，且排在推定平台宏**之后** —— 推定必须被实测覆盖；跨进程数据过字符白名单校验，不许打破文本结构）与变体选择升级（用编辑器实际启用的那个关键字选变体）。
5. **结构纪律**：传输层不引用编辑器 API（想违反也没有入口）；后台线程只读主线程预热好的缓存值（编辑器大量 API 只能在主线程调用）；编码器是纯函数，可在任意线程调用。接收循环对非关闭类异常只记日志并继续，单个客户端接入失败不影响其它连接。
6. **发现文件有 schema 文件作单一真相源**：读端代码、桥接脚本与文档三方以同一份字段约定为准，漂移无处藏身。
7. **菜单六项**：状态 / 启用禁用 / 重启监听 / 立即广播 / 打开发现文件 / 详细日志开关。

### 保证与限制

- 黄金判据：桥接开 / 关诊断逐条相同（零 Error）；编辑器域重载后端口重新绑定成功、发现文件不被删除。
- 两条被实测教训钉住的排障经验：其一，「TCP 连得上但一帧收不到」先怀疑**服务端用户态接收循环是否还活着**，而不是网络 —— 内核完成握手 ≠ 应用已接受连接；其二，「什么都没发生」要当故障处理：功能未启用或连接失败也必须留下一条人读原因，让用户能区分「没装」「装错了」「装好了但没连上」。
- 断线即回退：连接断开后服务端自动回到「未绑定桥接」的正常模式，无需重启。
- 边界：`.hlsl` 不在桥接范围；同一工程开两个编辑器没有引用计数；Unity 被强制结束后残留的发现文件属预期退化。
- 回归覆盖：自检里有专门的桥接套件（发现 / 判活 / 载荷 / 契约 / 回环 / 装配六个方面），真机回归另有冒烟脚本。

### 代码入口

- `client/unity/MicroShaderBridge/BridgeServer.cs` —— Unity 侧监听与广播
- `src/MicroShader.ContextEngine/UnityBridgeClient.cs` —— 服务端侧外连与去重

## 构建、发布与交付流水线

**功能一句话**：从源码到「可以交给用户的东西」的完整流水线：发布原生可执行文件、装配编译器与许可证、跑门禁、打包客户端安装包。

### 怎么工作

发布与交付按 S1~S7 七步执行（编号是这份交付清单的步号，直接按序照做）：

- **S1 锁定编译器版本**：只从锁定版本的官方发布包取 DLL，并登记每个文件的哈希 —— 换一台机器装了别的 SDK 也不会静默换版本。现状说明：实际随包交付的两个 DLL 是 Windows SDK 构建，与官方发布资产字节不同；哈希锁已登记实际交付件，「是否切换到官方发布资产」仍是待决策项。
- **S2 随包交付许可证**：编译器发行版是 UIUC/NCSA（LLVM）许可，三个许可证文件 + 头文件必须随包交付；许可证文本必须从官方包**逐字节取**，绝不凭记忆转录。
- **S3 交付指纹**：生成 `checksums.txt`，对交付目录内每个文件列 SHA-256 —— 用于缓解「原生可执行文件无商业签名 → 杀软启发式误报」。
- **S4 双配置发布**：保真的诊断版与「体积优先」版两种发布配置；体积优先会牺牲异常消息可读性，与「排障优先」相抵 —— 若实测收益低于 5%，建议只发诊断版。
- **S5 门禁加固**：在「调试符号归档、原生依赖同目录、真加载编译器」三道基础闸门之上再加四道：哈希锁校验；系统路径上不得出现第二份编译器 DLL（否则「到底加载了哪一份」无法断言）；交付目录内文件集合精确断言（多一个少一个都熔断）；版本命令输出必须自证「来源同目录」。
- **S6 客户端打包**：注入可执行文件与编译器 → 打包成扩展安装包；打包后必须断言二进制**真的在包内**（打包工具可能按默认排除规则把目录排除掉）；打包路径避开空格与中文。
- **S7 回归断言**：体积上限与「冷启动到初始化完成」的耗时上界进流水线。

配套的维护习惯：发布脚本先清理旧产物再发布（调试符号残留由此防住）；三套入口（PowerShell / 命令行批处理 / shell）是等价入口，改一必须同改三；交付产物目录与安装包不入库（可再生产物），流水线脚本入库。

### 坑表（都是实测踩过的）

| 坑 | 现象 | 对策 |
| :-- | :-- | :-- |
| 调试符号残留 | 发布后交付目录多出多个 PDB（调试符号）文件 | 发布前清目录；「排除单文件」类属性对原生发布不适用 |
| `.cmd` 脚本 | 中文注释 + LF 换行会被命令解释器误当命令解析 | `.cmd` 必须纯 ASCII + CRLF 换行；`.ps1` 用 UTF-8 无 BOM |
| `Assembly.Location` 判断原生发布 | 原生发布下该属性为空（相关分析器会直接把编译拦掉） | 改用「可执行文件旁是否还有同名 .dll」判断，物理事实、不依赖运行配置 |
| PipeWriter 流所有权 | 包装流时默认**接管并关闭**传入的流 —— 在标准输入输出宿主里关掉的是进程的标准输出，收尾刷新时抛异常、原生进程直接崩溃 | 显式声明不接管（`leaveOpen`），传输层不拥有调用方的流 |
| `PublishAot` 写进工程文件 | 会把「不支持动态代码」写进运行配置，连普通运行都自称不支持 | 刻意不写进工程文件，发布时用命令行参数开启 |

### 代码入口

- `scripts/publish-aot.ps1` —— 发布与三闸门（与 `.cmd` / `.sh` 两套入口必须同步修改）
- `scripts/package-vsix.ps1` —— 扩展打包

## 自检体系与基线

**功能一句话**：一条命令在无头环境跑完全部回归（固定语料、真实 URP 语料、协议回环、桥接契约、原生发布回环），按退出码挂 CI。

### 怎么工作

- 用例按依赖等级分五类：行为（无外部依赖）、真机（需真实工程）、协议回环、桥接契约、原生发布回环。
- 命令面：不带参数即全量；`--filter <子串>` 按套件 / 用例名过滤；`--list` 只列用例名；`--analyze <文件>` 手动跑一遍单文件管线（切片 → 装配 → 编译 → 归属）并打印最终诊断，配套 `--line`（指定探针行）、`--type`（打字快路径）、`--emit`（打印装配后的渲染文本）。
- 真机类用例用环境变量指定素材：`MICROSHADER_UNITY_PROJECT`（真实 Unity 工程）、`MICROSHADER_URP_ROOT`（本机 URP 包目录，也可用 `--urp` 覆盖）、`MICROSHADER_DXC_DIR`（编译器 DLL 所在目录）；缺失时相关用例记「跳过」，不影响退出码。
- 常用过滤关键字与能力一一对应（如 `IntelliSense`、`Navigation`、`Attribution`、`Compile`、`Tag`、`Bridge`、`Server`），全名用 `--list` 查。
- 退出码：0 全绿；1 存在失败用例；2 `--analyze` 的前置条件不满足；报告先看「失败」列再看「跳过」列 —— 只有失败影响退出码，跳过表示环境素材缺失。
- **计数口径：用例总数以 `--list` 为准**，套件分布与通过数以运行输出为准 —— 本文不复制具体数字（会腐烂）。
- 用例用静态注册的方式加进套件；新增用例的语料放在 `tests/Fixtures/`。
- 测量类结论的准入纪律（负面结论先过装置自检）见 [`docs/testing-guidelines.md`](testing-guidelines.md)；提交前跑法与 CI 口径见 [`CONTRIBUTING.md`](../CONTRIBUTING.md)。

### 保证与限制

- 完整环境（环境变量齐备）下应全绿、无已知的既有失败；输出结尾固定打印「合计 / 通过 / 失败 / 跳过」，可直接挂 CI；全量运行在 Release 构建下执行。
- 两类「偶发红」要先区分再下结论：防抖类用例对系统时钟敏感（机器被占满 CPU 时，连打循环被抢占会误红），属测试设计依赖而非产品缺陷；排查前先确认机器负载。
- 已知缺口：统一报表出口未实现 —— 读数目前只有标准输出文本，没有机器可读的基线文件与自动对比；受限环境（无真实工程）下「全绿」可能由大量「跳过」构成，没有最低执行条数门禁。
- 场外基准工具与历史读数不入库，干净克隆不可复现（它们只服务于本机回归）。
