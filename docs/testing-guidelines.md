# 开发规范 · 装置自检（测量类结论的准入规则）

> 适用：任何由探针 / 测量工具得出的能力结论，尤其是负面结论。「装置」在本文件里指测量工具本身——
> 探针脚本、测试台这类东西，不是被测对象。
> 历史背景：本项目曾连续六次把「测量工具自身的毛病」误判成「技术不可行」（过程见 Git 历史），
> 因此立下这条纪律。

---

## 一、铁律

**任何负面结论（「补不出来」「不可用」「不支持」「0 候选」）在采信之前，必须先通过装置自检；
没有自检的负面结论一律视为无效，不得进入决策。**

理由：本项目的探针链路上，**装置的默认行为太容易给出「看似结论」的假信号**。
正面结论（「能补出来 + 看到具体标签」）自带证据，风险低；负面结论只是「没看到东西」，
而「没看到东西」有六种已证实的伪因。

**性能数字同理：单次读数不算结果。** 自检与探针都是 .NET 进程，第一轮里含即时编译（JIT）预热
与缓存冷启，测出来偏快偏慢都常见——只跑一遍，测到的往往是「预热过程」而不是真实性能。
必须先跑预热轮次、丢掉前几轮，再多轮取中位数；只报「最好一次」或「最差一次」，和没测一样。

## 二、六例实证（每一例都曾被误读成「技术不行」）

| # | 伪因 | 真相 | 误读后果 |
| :-: | :--- | :--- | :--- |
| 1 | 内联器只认 `#include "`，不认 Unity 的 **`#include_with_pragmas`** | 该文件**从未被内联**，TU 只剩 0.3 KB → 符号全不可见 | 判「751 KB 后 codeComplete 空返 = 路线不可行」 |
| 2 | 内联器不解析**相对 include**（`"Common.hlsl"`），解析不到就**整行静默丢掉** | URP 头被掏空 → `Light` 等类型缺失 | 判「DXC 补不出 URP 类型」 |
| 3 | 探针标记把 `;` 也包进去，**光标落在 `;` 之后** | 变成「语句边界」补全，返回 1008 条**无前缀过滤的全量** | 差一点判「前缀补全成功」 |
| 4 | 「**拼文本**」装配的预处理语义不等价（不做 `#if` 求值、丢 include） | 35 条诊断、`Light` 不可用；而正确装配只有 2 条 | 把装配缺陷当成路线能力差异 |
| 5 | 照搬**编译参数**（`-T ps_6_0 -E frag -HV 2018 -Zpc`）喂给 `ParseTranslationUnit` | 四种装配**全部 E_FAIL(0x80004005)**，parse 根本起不来 | 判「缺参数所以没候选」 |
| 6 | 怀疑「覆盖/磁盘装配的文件名拼写不匹配」，逐一试了 6 种文件名形态 | **全部 0**。真相是装置约束：**只有「整棵 include 树拼进 unsaved 缓冲」才给候选**，磁盘解析 include 一律 0 | 差点把装置约束当成 `-I` 的锅 |

## 三、自检清单（负面结论采纳前必须做完）

1. **本地对照物**：在同一份 TU、同一配置下，加一个**必然成功**的探针点。
   - 成员补全 → 用**同文件内刚声明的结构体**（如 `struct T { float3 a; float2 b; }; T t; t.`）；
   - 前缀补全 → 用**同函数内上一行刚声明的局部变量**。
   - 若对照物也是 0 → 结论无效，先修装置（本轮就是这样发现的：本地结构体在覆盖装配下也是 0）。
2. **打印候选标签**，不只看条数。
   - 条数会骗人：「5 条」实测是 `2 真字段 + 3 个 C++ 隐式成员`（`X::` / `~X()` / `operator=`）；
     「1008 条」是「无前缀过滤的全量」。
3. **打印带 `文件:行:列` 的诊断原文**，并**逐条解释**。任何 `unknown type name` / `invalid preprocessing directive`
   都要先归因到装置，再决定是否算能力。
4. **打印补全点前后 3 行**，肉眼确认光标真的在代码里、且落在预期 token 的位置。
5. **统计并打印「未解析的 include」**。解析不到就整行丢 = 静默丢文件，是第 2 例的根因。
6. **参数集最小化、失败先归因**：先只给宏，再逐个加目标/语言标志；一旦 HR 变成 `E_FAIL(0x80004005)`，
   先别下「此路不通」的结论——实测至少有两类诱因（入口函数标志、含空格的 `-I` 路径），
   定位清楚是谁引起的，再决定是否继续（第 5 例）。

## 四、同类缺陷检查法（五个方向，来自真实缺陷复盘）

改代码、查问题、验收时逐条过一遍（对应的修复都在代码与 Git 历史里，这里只留检查方向）：

1. **日志取值也要按类型设防。** 把外部输入（尤其是 JSON）的解析写进日志语句，就是把故障点藏进
   最不设防的地方：类型不符就会抛异常。凡解析外部输入的函数，必须对类型（不只是格式）设防——
   取不到就给可读的默认值和告警，而不是抛。
2. **关键配置显式传入，不靠「当前目录」猜。** 工作目录由宿主决定，换个打开方式（打开文件夹
   vs 打开单个文件）就会变，而且是静默退化。配置走显式参数或环境变量；每处「从运行环境推断出来的
   关键配置」都问一句：换一种启动方式还成立吗？
3. **「什么都没发生」要当故障处理。** 功能未启用、连接失败、请求被拒，都必须留下一条人能读的原因；
   否则用户无法区分「没装」「装错了」「装了但没连上」。沉默是最难查的失败。
4. **自动化判据必须回读真实状态。** 工具报的 `success: true` 只代表动作已派发，不代表结果正确；
   判据要回读日志、截图、进程或产物本身。
5. **读循环里不许有未兜底的异常。** 长时间运行的读循环、后台线程，任何未处理的异常都可能让进程
   直接消失（本项目是 Native AOT 构建，连崩溃转储都没有）：解析与处理要各自兜底，单条坏消息只回
   一个错误响应；兜底代码自身也不许再抛，而且要落盘留痕——修「不再崩」的同时必须保住「可发现」。

## 五、两条与产品选型有关的长期结论

由实测直接得出，与探针本身无关：

1. **补全接口的解析参数要单独维护**，不要与编译参数共用一份：实测编译参数里的入口函数标志（`-E`）
   会让 DXC 的补全接口 `ParseTranslationUnit` 直接 `E_FAIL`，带空格的 `-I` 路径同样会触发它。
2. **不要用手工拼接的整段文本代替真正的 include 解析。** 保留 include 原文、交给 DXC 按自己的规则
   解析，预处理语义才正确：手拼版本产生 35 条诊断，正确装配只有 2 条。
   另有两个实测限制要一起记住：这类补全接口只对以内存缓冲提供的主文件返回候选，磁盘上的主文件
   静默返回 0 条；而语义正确的装配形态给不出候选，能给出候选的形态语义又不正确。
   将来要采用这类补全引擎，必须先解决它们。

## 六、一句话

**「没看到」不等于「不存在」。先证明装置会「看到」，再声明东西不存在。**
